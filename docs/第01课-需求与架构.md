# 后端与数据库

前端用原生 JavaScript，后端用 Flask，数据存进 SQLite。页面和 API 由同一个服务提供。

## 一颗棋是怎么下出去的

点击棋盘后，前端向 `/api/games/<id>/moves` 发起 POST 请求：

```json
{"row": 9, "col": 9}
```

`app.py` 的 `place_one()` 检查回合、坐标和占用情况，通过后写入数据库，再判断胜负。前端拿到返回的棋局重新画棋盘。

玩家下完一回合后，前端请求 `/ai-turn`。后端按本局保存的 `human_color` 确定 AI 颜色，逐颗下完本回合的棋。玩家执白时，开局由黑方 AI 先下一颗。任意一颗成六就停止。

## 为什么保存每颗落子

`moves` 按 `game_id` 和 `move_no` 保存颜色、行、列。读取时按顺序还原棋盘，回放、导出和复盘都用这份数据。

数据库表的分工：

| 表 | 内容 |
| --- | --- |
| `games` | 棋局编号、状态、胜者、创建时间、对手类型、玩家颜色 |
| `moves` | 落子顺序、坐标、颜色、AI 来源、原因和耗时 |
| `analyses` | 复盘结果，关联棋局和当时的落子数量 |
| `submissions` | 上传的 AI 名称、语言、源码哈希和时间 |
| `arena_matches` | 对战版本、挑战方颜色、执行状态和终局原因 |

AI 挑战由 `arena.py` 的后台队列运行。前端只负责上传和轮询，不参与计时或胜负判断。`sandbox_runner.py` 在容器里编译和运行代码，每拿到一颗合法落子就调用同一个 `place_one()`，随后保存耗时并检查终局。关闭网页后比赛仍会继续。

继续下棋后，之前的复盘仍保存在数据库里，但当前页面只显示与最新棋谱匹配的结果。

## 刷新恢复

前端把当前棋局 ID 写进 URL 和 localStorage。刷新后使用这个 ID 请求 `/api/games/<id>`，从 SQLite 取回棋谱和分析结果。

数据库在 `data/connect6.db`。`init_db()` 会建表，并为旧版数据库补上新增字段。

## 调试

打开浏览器开发者工具的 Network 面板，下一颗棋，查看 `/moves` 的请求体和响应。再刷新一次，查看恢复棋局的 GET 请求。

完整路由见 [接口说明](接口说明.md)。
